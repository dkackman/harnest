# R8: port the drivers to Python, along R13's profile line

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the bash drivers with a Python package that behaves the same, reads a
target profile from its first module, and keeps every env knob, log line and state file
name.

**Done when:**
- The bash drivers and `providers.sh` are deleted.
- Provider handling lives in one Python module.
- The dw loop's behaviour and costs are unchanged across the switch, checked by the offline
  suite and by at least a day of live cycles per driver.

**Spec:** `docs/superpowers/specs/2026-09-27-r8-port-inputs.md` (inventories in
`docs/superpowers/specs/2026-09-27-r8-inputs/`).

**Follows the decisions Don accepted on 2026-09-28** (spec, "Decisions"): 1 Python first,
SDK later; 2 harnest#15's "target" becomes "server"; 3 `targets/dw/` in this repo; 4 the
guard stays a command hook; 5 release is a plug-in, ported last. Phase 1's departure from
R13's sequencing was accepted with them.

## Global constraints

- **The lem loop is live throughout.** The dos and don'ts:
  - Never edit a running driver.
  - Phases 0–4 add files, and edit bash only where the plan says so, between runs.
  - A Python module is read once at import, so the byte-offset hazard of editing a live
    driver goes away once the loop itself is Python. A lazy import can still pick up a
    half-edited file, though, so import everything at startup.
  - **Edit `providers.sh` and `lib/` only with the loops stopped** (`stop-after-cycle`). The
    "don't edit a live driver" rule covers the drivers, but a running loop starts child
    drivers (`run-features.sh` from `features_pass`, `run-regression.sh` from the nightly
    pass). Each of those sources `providers.sh` fresh, so a parent on old code would start
    children on new code.
- **The entry points keep their names.** Each `run-*.sh` becomes a three-line shim:
  `exec python3 -m harness.drivers.<name> "$@"`. That keeps `tests/test-drivers.sh`, the
  dashboard's `DRIVER_RE`, cron entries, the README and muscle memory.
- **Stdlib only** until the SDK phase: `tomllib`, `subprocess`, `json`, `argparse`,
  `pathlib`. No venv. The harness runs on this Mac's `python3` (3.13).
- **Log lines and state file names are a contract** (spec, "The log format is a contract").
  Any change to one is a separate, deliberate commit that updates its readers in the same
  commit.
- **`tests/run.sh` must pass after every task.** New Python code gets `pytest`-free unit
  tests in `tests/py/` run by `python3 -m unittest`, and `tests/run.sh` gains a
  `test-python.sh` that runs them. That keeps the runner dependency-free.
- **Every external tool stays a subprocess** through one seam module each (`gh.py`, `git.py`,
  `ssh`/`curl` in `deploy.py`, `claude` in `session.py`), so `fake-gh.py` and the PATH stubs
  keep working.

## Phase 1 — the profile, still read by bash

**This departs from R13 on purpose.** R13's "Sequencing with R8" says step 1 in bash is
worth doing only if R8 slips. The difference here:
- `profile.py` and `profile.toml` are permanent; only their bash reader is temporary, and it
  is a few lines.
- Wiring them into the bash drivers runs the whole offline suite against the profile before
  any Python driver exists. A missed dw constant then shows up as a failing bash test, not as
  a mismatch in the side-by-side runs later.

If Don prefers R13's order, skip the `providers.sh` task and move the second-profile test into
Phase 2.

- [ ] Write `targets/dw/profile.toml` with every field in the spec's "The target profile",
  including the servers table.
- [ ] Add `harness/profile.py`, which loads and validates the profile. Add
  `python3 -m harness.profile --shell <server>`, which prints `KEY=value` lines. Also add a
  `tests/py/test_profile.py` round-trip.
- [ ] Have `providers.sh` read the profile through that command, via a temp file and `.`,
  since bash 3.2 has no `source <(…)`. It replaces the hard-coded defaults in
  `resolve_target`, `deploy_cmd` and `deployed_head`, plus `TICKET_REPO`, `HARNESS_REPO` and
  `TICKET_OWNER`. Env vars still override, so the knob contract holds.
- [ ] Give `fake-gh.py`'s tests a **second profile** (`tests/fixtures/profile-other.toml`, a
  made-up target), and run `test-drivers.sh`'s fix-then-verify scenario under it. Every
  failure is a dw constant the profile missed.

## Risks

- **Parity gaps the tests don't cover.** The fake `gh` returns `[]` for unknown `gh api`
  paths, so bounce escalation and parking are tested only as units, never end to end (a
  `code.md` surprise). Add a `timeline` endpoint to `fake-gh.py` in phase 2, before the loop
  port relies on it.
- **Error semantics.** The drivers lean on `set -e` exemptions, `|| true` and
  "always returns 0" functions. Port them pass by pass, and state each one's failure policy
  in the function.
- **BSD-only calls** (`date -r`, `date -v`, `find -mmin`, `sed -u`, `perl alarm`) disappear.
  That's welcome, but the behaviour of each one must be checked, not assumed.
