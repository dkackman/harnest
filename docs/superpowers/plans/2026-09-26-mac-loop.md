# The loop on another server: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `DW_TARGET=local ./run-loop.sh` runs the implementer/tester loop against a dw
server on this Mac (MPS), alongside or instead of the loop on lem, without the two ever
working the same issue and without the Mac loop reaching lem.

**Architecture:**
- **Issue scope.** `lib/classify.jq` learns which loop is asking (`target`) and holds any
  issue that isn't this loop's at `wait`. What makes an issue this loop's: its
  `target:` claim, its `backend:` label, and a legacy rule for issues handed off before
  claims existed.
- **Per-target resources.** `providers.sh` resolves each target's clones, deploy
  command, state files and log.
- **Mac loop behaviour.** `run-loop.sh` claims issues, deploys through that command, and
  runs the server-free passes only when the lem loop is off.
- **Enforcement.** `guard.py` enforces the rules a mistake couldn't be taken back from.
- **Prompt additions.** Role prompts get a target section per role, the same way the
  regression agent already does.

**Tech Stack:** bash 3.2 (macOS `/bin/bash`), jq, python3 (guard), `gh`, the offline test
suite in `tests/` (fake gh board, stub ssh/claude/curl).

**Spec:** `docs/superpowers/specs/2026-09-26-mac-loop-design.md`

## Global Constraints

- Every driver must still parse under `/bin/bash` 3.2:
  - no `source <(…)`;
  - no apostrophe in a comment inside `<( )`;
  - no apostrophe inside `${VAR:+…}` within double quotes.
- `tests/run.sh` passes before every commit that touches a driver, `providers.sh`,
  `lib/classify.jq` or `guard.py` (CLAUDE.md).
- Every new `${KNOB:-}` a driver reads is named in README's settings table
  (`test-lint.sh` enforces this).
- For `DW_TARGET=lem`, every existing name stays as it is: lock, logs, state files,
  defaults. A lem loop started after this change behaves as before, except for three
  things:
  - it skips `backend:mps` and `target:local` issues;
  - it claims issues as `target:lem`;
  - its triage adds `backend:` labels.
- Nothing in the Mac loop runs `ssh`, and no Mac-loop session may run it either.
- Labels, exactly:
  - `backend:shared`, `backend:cuda`, `backend:mps`;
  - `target:lem`, `target:local`;
  - `verified-on:mps`.
- Defaults on local:
  - `SOURCE_DIR=~/src/dkackman/dw-agent-mps`
  - `PLUGIN_TREE=~/src/dkackman/dw-agent-plugin-mps`
  - `LEAD_TREE=~/src/dkackman/dw-agent-lead-mps`
  - `DW_LOCAL_DIR=~/src/dkackman/dw-mps-serve`
  - `DW_LOCAL_WORKSPACE=~/dw-mps-workspace`
  - `TESTER_BUDGET_USD=8`
- Commit straight to `main` in this repo (Don, 2026-09-26). In the dw repo, push a
  branch only. Don merges it.
- lem is off limits: no ssh, no MCP call, no deploy to lem in any manual step of this
  plan.

## Review Focus

1. **The lem backlog on the Mac loop.** An unclaimed `owner:tester` +
   `status:fixed-pending-verify` issue was deployed to lem, so the Mac loop must show it
   as `wait`. The Mac tester must never verify it. Test: Task 1, board "legacy".
2. **A contradictory label pair.** `target:local` on a `backend:cuda` issue should be
   `stranded`, so the audit warns, rather than silently worked on the Mac. Test: Task 1,
   board "claims".
3. **Two loops claim the same issue in the same second.** Both labels end up present,
   lem keeps it, and the Mac loop drops its own claim and skips the issue. The Mac
   session re-checks just before it starts. Test: Task 5, driver scenario "tie".
4. **A failed local deploy** (dirty serving clone, server won't start). The failure is
   logged, the tester still runs, and the prompt names what is actually running. Test:
   Task 5, driver scenario "deploy fails".
5. **A Mac regression run started while the Mac loop is mid-cycle.** It waits on
   `.driver.lock.local`, and lem's lock is untouched. Test: Task 5, driver scenario
   "regression waits on the Mac loop".

# claim_issue <n>
# Marks <n> as this loop's (target:<DW_TARGET>) and reads it back. Two loops
# can read an issue as unclaimed at the same moment; lem keeps a tie, and
# the other loop removes its own label. 1 when this loop doesn't hold it.
claim_issue() {
  local n="$1" labels
  gh issue edit "$n" --repo "$TICKET_REPO" --add-label "target:$DW_TARGET" >/dev/null 2>&1 || return 1
  labels="$(gh issue view "$n" --repo "$TICKET_REPO" --json labels --jq '.labels[].name' 2>/dev/null)" || return 1
  printf '%s\n' "$labels" | grep -qx "target:$DW_TARGET" || return 1
  if [ "$DW_TARGET" != lem ] && printf '%s\n' "$labels" | grep -qx target:lem; then
    gh issue edit "$n" --repo "$TICKET_REPO" --remove-label "target:$DW_TARGET" >/dev/null 2>&1 || true
    return 1
  fi
}

# lem_loop_running: the lem loop holds its lock now (not a regression run).
lem_loop_running() {
  local pid name
  read -r pid name < "$LOGS/.driver.lock/owner" 2>/dev/null || return 1
  [ "$name" = run-loop ] && kill -0 "$pid" 2>/dev/null
}
